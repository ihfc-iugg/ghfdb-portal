# Bug Report: Import Confirm Page Displays AUTO_PARENT Key Instead of local_id

**Type**: Implementation drift
**Severity**: Medium
**Feature**: 003-ghfdb-import-export
**Reported**: 2026-04-15
**Status**: Patched
**Patched**: 2026-04-15

## Description

On the Django admin import confirm page (the review/dry-run step shown before the user clicks "Confirm Import"), the `ID_parent` column displays the synthetic `AUTO_PARENT:<lat>:<lon>` key rather than the actual `ParentHeatFlow.local_id` value.

**Observed**: `ID_parent` cell shows `AUTO_PARENT:-8.0605:114.24438`
**Expected**: `ID_parent` cell should show the `local_id` value of the parent record (e.g. a GHFDB spreadsheet ID or a meaningful site identifier)

The synthetic key is an internal implementation detail of the template-aware upsert fallback (BUG-003 fix). It is injected into `ID_parent` by `before_import_row()` to satisfy `import_id_fields` header validation and drive the upsert lookup. However, it leaks into the confirm-page diff view that django-import-export renders to the user, replacing what should be a human-readable identifier.

## Root Cause Analysis

`before_import_row()` unconditionally overwrites `row["ID_parent"]` with `_effective_parent_id()`, which returns either the explicit spreadsheet value (if present) or the synthetic `AUTO_PARENT:<lat>:<lon>` fallback. django-import-export uses the row dict — including this overwritten value — to build the confirm-page diff table. The synthetic key was designed as a private upsert handle, not a display value, but no separation exists between the internal upsert key and the value rendered to the user.

The fix should ensure that:

1. The internal upsert key (used by `import_id_fields`) is the `AUTO_PARENT:` value when no explicit ID is present.
2. The displayed `ID_parent` on the confirm page is either the original spreadsheet value or the `local_id` that will be assigned to the `ParentHeatFlow` record (e.g. derived from the site name or left blank if not available).

One clean approach: store the synthetic key in a separate, non-displayed field (e.g. `_upsert_key`) and keep `ID_parent` as the user-visible identifier mapped to `ParentHeatFlow.local_id`.

## Recommended Fix

1. **parent.py**: Remove `_effective_parent_id`, `_normalize_decimal`, and `before_import_row`. Deduplicate in `before_import()` by lat/lon tuple directly. In `_get_or_create_site()`, look up existing sites by `location__x` / `location__y` when `ID_parent` is empty. Leave `local_id` empty for template rows.
2. **child.py**: Remove `_effective_parent_id`, `_effective_child_id`, `_normalize_decimal`, and `before_import_row`. Add `_resolve_parent_by_location()` to look up `ParentHeatFlow` via `HeatFlowSite.location` when `ID_parent` / `ForeignKeyWidget` returns no match.
3. Update tests to assert no `AUTO_PARENT:` / `AUTO_CHILD:` prefixes appear in `local_id` fields after import.
