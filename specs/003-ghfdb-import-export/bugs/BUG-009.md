# Bug Report: geo_stratigraphy Import Fails with "Field 'id' expected a number but got <gts2020: Holocene>"

**Type**: Spec gap (data model mismatch between import contract and actual model field definition)
**Severity**: High
**Feature**: `003-ghfdb-import-export`
**Reported**: 2026-04-16
**Status**: Patched
**Patched**: 2026-04-16

---

## Description

When importing a GHFDB spreadsheet row where `geo_stratigraphy` contains the value `"Holocene"`, the import pipeline raises the following error:

```
Line number: 1 - Field 'id' expected a number but got <gts2020: Holocene>.
```

The error `<gts2020: Holocene>` is the `repr()` of a `research_vocabs.Concept` instance whose vocabulary name is `gts2020` (ICS Geological Time Scale 2020) and whose concept name is `"Holocene"`. Django's `IntegerField.to_python()` raises this error when a `Concept` object is passed where an integer ID is expected.

---

## Root Cause Analysis

The bug is a **model mismatch** between what the import contract specifies and what the actual `HeatFlowInterval` model field definition contains.

### The mismatch

The import contract (`contracts/import-contract.md`, row 14) specifies:

```
geo_stratigraphy → HeatFlowInterval.stratigraphy via MultiConceptWidget(GeologicalTimescale)
```

`IntervalWidget.m2m_map` in `widgets.py` implements this as:

```python
"stratigraphy": (
    "geo_stratigraphy",
    MultiConceptWidget(GeologicalTimescale),
),
```

`MultiConceptWidget(GeologicalTimescale).clean("Holocene")` returns a **`research_vocabs.Concept` queryset** filtered by the `GeologicalTimescale` vocabulary.

However, the actual `HeatFlowInterval` model field (confirmed in `project/heat_flow/migrations/0001_initial.py`, line ~191) is:

```python
"stratigraphy",
models.ManyToManyField(
    blank=True,
    help_text="The stratigraphy of the interval.",
    to="stratigraphy.stratigraphicunit",      # ← points to StratigraphicUnit, NOT Concept
    verbose_name="stratigraphy",
),
```

This is **not** a `ConceptManyToManyField` and does **not** point to `research_vocabs.Concept`. It is a standard Django M2M to a separate `stratigraphy.StratigraphicUnit` model.

Compare with the adjacent `age` and `lithology` fields which are correctly defined as `ConceptManyToManyField`:

```python
"age",
research_vocabs.fields.ConceptManyToManyField(
    blank=True,
    to="research_vocabs.concept",
    vocabulary=fairdm_geo.vocabularies.stratigraphy.GeologicalTimescale,  # ← SAME vocab
),
"lithology",
research_vocabs.fields.ConceptManyToManyField(
    blank=True,
    to="research_vocabs.concept",
    vocabulary=fairdm_geo.vocabularies.cgi.geosciml.SimpleLithology,
),
```

### Failure mechanism

When `set_m2m_relations()` in `IntervalWidget` calls:

```python
interval.stratigraphy.set(concept_qs)  # concept_qs → research_vocabs.Concept objects
```

Django's M2M `set()` attempts to process `research_vocabs.Concept` objects for a relation that expects `stratigraphy.StratigraphicUnit` instances. The resulting error — "Field 'id' expected a number but got `<gts2020: Holocene>`" — occurs because Django's M2M machinery attempts to pass a `Concept` object (`repr: <gts2020: Holocene>`) to `StratigraphicUnit.id` (an `IntegerField`).

Note: `set_m2m_relations()` catches `(ValueError, ValidationError)` but **not** the `TypeError`/`IntegerField` error triggered by a cross-model M2M type mismatch, so the error propagates unhandled to the import pipeline.

### Why only "Holocene" (non-empty values)

The `set_m2m_relations()` guard `if raw:` means the bug is only triggered when `geo_stratigraphy` is **non-empty**. All existing tests use `"geo_stratigraphy": ""` (empty string), so the error was never exercised in the test suite.

The import contract was written as if `stratigraphy` were a `ConceptManyToManyField`, but the actual model has it linking to a different model.

### contracts/import-contract.md

- **Affected row**: Row 14: `geo_stratigraphy | concepts | O | HeatFlowInterval | stratigraphy | MultiConceptWidget(...) | M2M.`
- **Gap**: The `stratigraphy` target field is documented as accepting `MultiConceptWidget(GeologicalTimescale)` output (i.e., `research_vocabs.Concept` objects), but the actual model field `HeatFlowInterval.stratigraphy` is `ManyToManyField(to="stratigraphy.stratigraphicunit")` — a different model. The correct target field for `GeologicalTimescale` concept imports is `HeatFlowInterval.age` (`ConceptManyToManyField(vocabulary=GeologicalTimescale)`).

### plan.md

- **Affected section**: Widget hierarchy section — `IntervalWidget` in `widgets.py`
- **Impact**: Plan does not explicitly verify that M2M widget output types match the declared `to=` model of each M2M field on the target model.

### tasks.md

- **Affected task**: T034 — `IntervalWidget` implementation (marked `✅ Resolved`)
- **False completion**: T034 is marked resolved, but the `geo_stratigraphy → stratigraphy` mapping produces a runtime error for any non-empty stratigraphy value.
- **Missing task**: A new task is needed to either:
  1. Change `IntervalWidget.m2m_map["stratigraphy"]` to use key `"age"` instead (since `HeatFlowInterval.age` is the `ConceptManyToManyField(vocabulary=GeologicalTimescale)`), **OR**

## Recommended Fix

The fastest, lowest-risk fix:

**Change `IntervalWidget.m2m_map` to target `"age"` instead of `"stratigraphy"`**

In `project/ghfdb/resources/widgets.py`:

```python
# BEFORE (incorrect — HeatFlowInterval.stratigraphy → StratigraphicUnit, not Concept)
"stratigraphy": (
    "geo_stratigraphy",
    MultiConceptWidget(GeologicalTimescale),
),

# AFTER (correct — HeatFlowInterval.age → ConceptManyToManyField(GeologicalTimescale))
"age": (
    "geo_stratigraphy",
    MultiConceptWidget(GeologicalTimescale),
),
```

This works because `HeatFlowInterval.age` is already defined as:

```python
research_vocabs.fields.ConceptManyToManyField(
    to="research_vocabs.concept",
    vocabulary=GeologicalTimescale,
)
```

Which is exactly what `MultiConceptWidget(GeologicalTimescale)` produces. No migration is needed. The `stratigraphy` M2M (pointing to `StratigraphicUnit`) is separate and should remain unset until a dedicated `StratigraphicUnit` widget is built — or the field is assessed for removal.
