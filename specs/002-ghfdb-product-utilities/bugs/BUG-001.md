# Bug Report: explo_purpose Admin Filter Shows Unscoped Concept Values

**Type**: Spec gap
**Severity**: Medium
**Feature**: 002-ghfdb-product-utilities
**Reported**: 2026-04-14
**Status**: Patched
**Patched**: 2026-04-14

## Description
The `GHFDB` admin changelist includes `explo_purpose` in `list_filter`, but the rendered filter choices are sourced from the generic related `Concept` model and include values outside the accepted vocabulary for `HeatFlowSite.explo_purpose`.

At core, `explo_purpose` is an M2M relation to a generic `Concept` table. Using the default related-field admin filter on this relation surfaces broadly available concept values instead of constraining to the vocabulary accepted by the `explo_purpose` field.

Expected behavior:
- `explo_purpose` filter should show only allowed values for the `ExplorationPurpose` vocabulary accepted by the field.

Actual behavior:
- `explo_purpose` filter shows all values from the related generic concept model.

## Root Cause Analysis
Primary cause is a specification and test gap around generic-concept M2M list-filter semantics.

- `explo_purpose` is backed by a generic `Concept` relation.
- `list_filter` currently uses the raw relation path in `project/ghfdb/admin.py`, which delegates choice generation to default admin behavior.
- Default behavior does not enforce field vocabulary constraints for generic concept tables.
- The spec and tasks required filter presence but did not require constrained filter option scope, so this regression passed implemented checks.
