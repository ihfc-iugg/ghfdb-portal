# Bug Report: GHFDB Child Admin Filters Are Incorrect — Vocabulary-Unscoped ConceptFields and Broader Admin Class Gaps

**Type**: Spec gap / Untested flow
**Severity**: High
**Feature**: 002-ghfdb-proxy
**Reported**: 2026-04-20
**Status**: Patched
**Patched**: 2026-04-20

---

## Description

The GHFDB child admin changelist (`GHFDBChildAdmin`, registered on the `GHFDB` proxy model) now renders the correct column set (BUG-002 resolved), but the **list filters are semantically incorrect** and the admin class has a number of additional defects discovered during a holistic review. The primary issue is that the `environment` and `explo_method` filters are using raw Django `AllValuesFieldListFilter` (or `ChoicesFieldListFilter`) on `ConceptField`-backed CharField paths, rather than vocabulary-scoped custom filters. This is the same class of bug as BUG-001 (which fixed only `explo_purpose`), but BUG-001's fix was incomplete — it did not extend to the other concept-backed fields.

A secondary group of defects identified during full admin review includes: a silent wrong-type fallback in the `_interval()` helper, missing regression tests for filter queryset correctness, potential N+1 risks from column display methods that access `.all()` without prefetch confirmation, and a deep multi-MTI ORM traversal path that is valid but carries production performance risk.

---

## Bug 1 (Primary): `environment` and `explo_method` list filters are not vocabulary-scoped

### Actual behaviour

The `GHFDBChildAdmin.list_filter` entries for `environment` and `explo_method` use direct ORM path strings:

```python
"sample__heatflowinterval__sample__heatflowsite__environment",
"sample__heatflowinterval__sample__heatflowsite__explo_method",
```

Both `HeatFlowSite.environment` and `HeatFlowSite.explo_method` are `ConceptField` instances — a `CharField` subclass from `research_vocabs` that stores vocabulary keys as strings (confirmed by `max_length=20` / `max_length=16` in the migration). When Django admin renders list filters for a CharField, it uses `AllValuesFieldListFilter`, which queries all **distinct stored string values** from the database column. Because FR-016 normalises imported vocabulary values to lowercase, the stored keys may be lowercase codes (e.g., `"offshore"`, `"onshore_continental"`, `"borehole"`) rather than human-readable labels. The filter sidebar therefore shows these raw stored keys, not the vocabulary display labels.

This is the same root cause that motivated BUG-001 for `explo_purpose`, yet the BUG-001 fix introduced `ExplorePurposeListFilter` only for the M2M concept field and left the two CharField-backed concept fields (`environment`, `explo_method`) unfixed on both the child and parent admins.

The same issue exists on `GHFDBParentAdmin` for its `"sample__heatflowsite__environment"` and `"sample__heatflowsite__explo_method"` filter entries.

### Expected behaviour

Per FR-015:
> "For concept-backed admin list filters on **both** admins, filter options MUST be constrained to vocabulary-accepted values for the target field."

`environment` should offer choices labelled by the `GeographicEnvironment` vocabulary. `explo_method` should offer choices labelled by the `ExplorationMethod` vocabulary. Both should display human-readable labels, not raw stored keys.

### Root Cause

BUG-001 resolution used a custom `SimpleListFilter` to scope `explo_purpose` choices, but this pattern was not applied to the other two concept-backed fields on the `HeatFlowSite` model. FR-015 was read narrowly (only `explo_purpose` was explicitly called out in the requirement text), missing the general intent that ALL vocabulary-backed filter fields require scoped choices.

## Bug 2 (Secondary): `_interval()` helper uses a wrong-type silent fallback

### Actual behaviour

The `GHFDBChildAdmin._interval()` static method is:

```python
@staticmethod
def _interval(obj):
    sample = getattr(obj, "sample", None)
    if sample is None:
        return None
    return getattr(sample, "heatflowinterval", sample)
```

The fallback `getattr(sample, "heatflowinterval", sample)` returns the raw `Sample` base-model object when the `heatflowinterval` MTI child accessor does not resolve (e.g., `RelatedObjectDoesNotExist`, or a `Sample` record that is not a `HeatFlowInterval`). Callers such as `get_geo_lithology`, `get_geo_stratigraphy`, and `get_probe_type` then receive a `Sample` instance, access `.lithology.all()`, `.stratigraphy.all()`, or `.probe_metadata` on it — all of which will either raise `AttributeError` or silently return `""` due to their own `hasattr`/`getattr` guards. The net effect is that these columns silently return empty values for any record where the MTI accessor fails, with no error surfaced.

### Expected behaviour

The helper should either return `None` (not the `Sample` fallback) when `heatflowinterval` is not accessible, or re-raise `RelatedObjectDoesNotExist` so callers can handle it explicitly. The current fallback masks data integrity problems.

### Root Cause

The `getattr(sample, "heatflowinterval", sample)` default was written to be defensive, but the default value `sample` is itself a wrong type — callers expect a `HeatFlowInterval` or `None`, not a `Sample`.

## Bug 3 (Secondary): List filter path traverses two MTI boundaries — not tested for correctness under filtering

### Actual behaviour

The child admin filter paths such as:

```
sample__heatflowinterval__sample__heatflowsite__country
```

traverse the `Sample → HeatFlowInterval` MTI reverse accessor and then the `HeatFlowInterval.sample → HeatFlowSite` MTI reverse accessor (two MTI hops). While Django ORM supports this pattern and the paths are structurally valid (confirmed by `as_ghfdb_flat()` using the same traversal for `F()` annotations), no test verifies that applying one of these filter paths to the actual admin queryset (i.e., `GHFDB.objects.as_ghfdb_flat().filter(sample__heatflowinterval__sample__heatflowsite__country="DE")`) returns correct results without SQL errors, cross-join amplification, or silent exclusion of records with NULL intermediate rows.

In production with thousands of records, the `AllValuesFieldListFilter` for `country` runs a `SELECT DISTINCT country FROM … JOIN heatflowinterval … JOIN sample … JOIN heatflowsite …` query each page load, which is non-trivial across three JOINs.

### Expected behaviour

Each list filter, when applied as a queryset `.filter()`, should return exactly the expected child records without cross-join amplification or incorrect exclusions, verified by at least one integration test per filter entry.

### Root Cause

The existing filter-path tests (T013) only assert that the correct ORM path strings appear in `model_admin.list_filter`; they do not call `.filter(…)` with each path and verify the resulting queryset count or content.

## Bug 4 (Secondary): `explo_purpose` filter in `ExplorePurposeListFilter` may return empty choices in a fresh database

### Actual behaviour

`ExplorePurposeListFilter.lookups()` calls `Concept.get_for_vocabulary(ExplorationPurpose).order_by("label")`. If the `Concept` table has not been populated (no vocabulary fixtures loaded), this returns zero choices and the filter sidebar shows nothing for `explo_purpose`. The test `test_explo_purpose_filter_choices_are_vocabulary_scoped` asserts `assert lookup_pks, "lookups() must return at least one choice"`, which would fail in a fresh environment. This is a known dependency on vocabulary fixtures that is not documented in the spec or quickstart and not enforced by the fixture setup.

### Expected behaviour

The `quickstart.md` or test `conftest.py` should document that vocabulary fixtures (or a management command) must be loaded before the `explo_purpose` filter produces any choices, and the test fixture should provide at least one `Concept` record from the `ExplorationPurpose` vocabulary.

---

## Bug 5 (Secondary): `corr_HP_flag` filter on child admin traverses parent FK — behaviour with `parent=None` records undefined

### Actual behaviour

The child admin filter `"parent__corr_HP_flag"` filters child `GHFDB`/`HeatFlow` records by the `corr_HP_flag` value on their linked `ParentHeatFlow`. Because `HeatFlow.parent` is nullable (`null=True, blank=True`), child records with `parent=None` are **excluded** by Django's default INNER JOIN behaviour when this filter is applied. No test covers this case.

### Expected behaviour

Filtering by `parent__corr_HP_flag` should either explicitly handle orphan child records (those without a linked parent) or the spec should document that only children with a linked parent participate in this filter.

## Root Cause Analysis

BUG-001 established the principle that M2M concept-backed filters need vocabulary scoping, but its implementation was scoped narrowly to `explo_purpose` (the only field explicitly mentioned in FR-015 by name). The concept-backed CharField fields `environment` and `explo_method` were left using Django's default AllValues filter, which exposes raw stored vocabulary keys. The test suite does not assert what values appear as filter choices — only that the filter entries are registered — so this gap was not caught during validation.

The `_interval()` fallback is a defensive coding pattern that inadvertently introduces a wrong-type return value, which propagates silently through column display methods.

## Recommended Fix

### Immediate (required to satisfy FR-014, FR-015, SC-003)

1. **Add vocabulary-scoped custom `SimpleListFilter` classes for `environment` and `explo_method`**:

   ```python
   class EnvironmentListFilter(SimpleListFilter):
       title = _("environment")
       parameter_name = "environment"

       def lookups(self, request, model_admin):
           from heat_flow.vocabularies import GeographicEnvironment
           from research_vocabs.models import Concept
           concepts = Concept.get_for_vocabulary(GeographicEnvironment).order_by("label")
           return [(c.notation or c.label, c.label) for c in concepts]

       def queryset(self, request, queryset):
           if self.value():
               return queryset.filter(
                   sample__heatflowinterval__sample__heatflowsite__environment=self.value()
               )
           return queryset

   class ChildExplorationMethodListFilter(SimpleListFilter):
       title = _("exploration method")
       parameter_name = "explo_method"

       def lookups(self, request, model_admin):
           from heat_flow.vocabularies import ExplorationMethod
           from research_vocabs.models import Concept
           concepts = Concept.get_for_vocabulary(ExplorationMethod).order_by("label")
           return [(c.notation or c.label, c.label) for c in concepts]

       def queryset(self, request, queryset):
           if self.value():
               return queryset.filter(
                   sample__heatflowinterval__sample__heatflowsite__explo_method=self.value()
               )
           return queryset
   ```

   Mirror these for `GHFDBParentAdmin` using the shorter `sample__heatflowsite__*` paths.

2. **Replace raw string entries in `list_filter`** on both child and parent admins with the new custom filter classes.

3. **Fix `_interval()` fallback**:
   ```python
   # Before:
   return getattr(sample, "heatflowinterval", sample)
   # After:
   return getattr(sample, "heatflowinterval", None)
   ```

4. **Update tests** (T013 / T065 equivalents) to:
   - Assert that `environment` and `explo_method` filter classes appear in `list_filter` (not raw strings).
   - Assert that `lookups()` on `EnvironmentListFilter` and `ChildExplorationMethodListFilter` returns vocabulary-scoped choices.

### Follow-up (recommended, not blocking)

5. Add integration tests that apply each list filter path to `GHFDB.objects.as_ghfdb_flat()` and verify the filtered queryset returns the expected subset of records.
6. Document vocabulary fixture dependency for `explo_purpose`, `environment`, and `explo_method` filters in `quickstart.md`.
7. Consider documenting `parent=None` orphan behaviour for the `corr_HP_flag` filter in spec/comments.
