# Bug Report: import_id_fields Uses ID/ID_parent Absent from Standard Upload Template

**Type**: Spec gap
**Severity**: High
**Feature**: 002-ghfdb-proxy
**Reported**: 2026-04-14
**Status**: Resolved
**Patched**: 2026-04-15
**Resolved**: 2026-04-15

## Description

**Follow-up (2026-04-15)**: Standard-template uploads still fail in one path before row-level fallback logic executes, with:

`The following fields are declared in 'import_id_fields' but are not present in the file headers: ID_parent`

The standard GHFDB upload template for individual datasets does **not** include `ID` or `ID_parent` columns. These identifiers are GHFDB database-level IDs assigned by the database maintainers when compiling an official release, not something individual dataset contributors provide.

Both import resources currently specify `import_id_fields` that depend on these missing columns:

- `GHFDBParentImportResource.Meta.import_id_fields = ("ID_parent",)` — the resource field `ID_parent` maps `attribute="local_id"` on `ParentHeatFlow`. When the upload template omits `ID_parent`, every row has `local_id=None`, and django-import-export cannot distinguish existing records from new ones. Re-importing the same file silently creates duplicates instead of upserting.
- `GHFDBChildImportResource.Meta.import_id_fields = ("local_id",)` — `local_id` maps to the `ID` spreadsheet column. Same failure mode: absent `ID` → `local_id=None` on all rows → upsert broken → duplicates on re-import.

The `_get_or_create_site()` helper in `parent.py` also falls through to an unconditional `HeatFlowSite()` creation when `id_parent` is empty, confirming that the parent resource has no fallback upsert path when `ID_parent` is absent.

**Expected behaviour**: A user uploads the standard individual-dataset template (no `ID`/`ID_parent` columns) twice. The second import updates existing records; no duplicates are created.

**Actual behaviour**: Standard-template imports can fail early with header-validation errors because `import_id_fields` declares optional `ID_parent` / `ID` fields that are absent from file headers.

**Suggested fix**: Remove `ID`/`ID_parent` from `import_id_fields` for both resources and use columns that are always present in the standard upload template. Use `lat_NS` + `long_EW` spreadsheet columns as the natural key for the parent resource. For child records, use a location/depth/publication-reference key (e.g., `lat_NS` + `long_EW` + `q_top` + `q_bottom` + `publication_reference`) so different references can submit distinct child heat-flow values over the same depth interval at the same site.

## Root Cause Analysis

The spec and plan were written with the official GHFDB release workflow in mind (round-trip: export → re-import the same file). In that context `ID` and `ID_parent` are always present. The individual dataset upload workflow — where contributors provide fresh data without pre-assigned GHFDB IDs — was not considered when FR-006 was drafted. As a result, both import resources were designed and implemented with `import_id_fields` that are only valid for the round-trip case, leaving the standard upload template path without a functioning upsert strategy.

The first patch added template-aware fallback matching, but did not fully account for django-import-export header-level `import_id_fields` checks. That left a remaining failure mode when optional ID headers are omitted entirely.
