3. What happens when a researcher uploads a dataset with a parent value that conflicts with the existing global parent value for a site?
4. How is provenance tracked in the GHFDB to indicate which dataset or measurement was used to select the global parent heat-flow value?
5. Are you changing researcher-submitted parent values when you "convert" them to global parent values, or are you simply changing which measurement is designated as canonical?
6. Do parent values get converted to child values (and vice versa)? If so, how? Given the different metadata structures.

## Key Points:

- One parent per location.
- Parent entries are fully-controlled by the database admins.
- Users upload child entries only.
- Users can upload as many children per site as they like
- Parents are representative values chosen by the database team after review.
  - For locations with single child entry, that child becomes the parent.
  - For locations with multiple child entries, the database admin team chooses. 
     - Typically an average of selected child entries, often favoring corrected values.
- When a user uploads a new child entry for an existing location, the database team needs to review and potentially update the parent entry.
- Existing parents should not be updated automatically when new children are added; updates are manual after review.
